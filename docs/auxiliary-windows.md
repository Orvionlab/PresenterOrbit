# Auxiliary windows

Settings, screen settings, and About use independent native windows without operating-system title bars. The shared dialog header is a native drag region for moving between monitors and supports double-clicking to maximize or restore. Header actions remain clickable, including the app's close button. Window edges remain resizable. Dragging permission is restricted to these registered subwindows. The main renderer prepares these windows invisibly at startup. Each window reports readiness after its content and saved settings have loaded; open requests made earlier wait for readiness without displaying the application splash screen. Closing a subwindow hides it and retains its renderer, so reopening immediately restores and focuses it without resetting its position or size. Settings panel requests are routed to that window, including requests received before readiness. Closing the main window destroys the auxiliary windows too.

The window kinds and their lifecycle live in `crates/orbit-app/src/auxiliary.rs` and `windows.rs`; each window hosts its own GPUI view (Settings, Screens, About) with the shared dialog header.

About accepts the `licenses` page in open requests, including before readiness. Its notices are generated by `orbit-app/build.rs` using Node.js and `scripts/generate-rust-notices.mts` for the Cargo target, then embedded in the executable. Development builds show the same notices without requiring packaging or filesystem reads when the page opens. Cargo regenerates them when the lockfile, workspace manifests, or generator changes. Packaged distributions also retain the standalone notices file.

To add a window:

1. Add its kind to the shared contract and native allowlisted registry, defining its title and initial/minimum dimensions.
2. Register its content in `AuxiliaryWindowsBridge` and connect its open state to `AuxiliaryWindowLauncherBridge`.
3. Use `Dialog standalone` and close through `closeAuxiliaryWindow`.
4. Test the native launch, isolated content, and close behavior.

Auxiliary windows use the existing settings runtime composition. It loads settings and subscribes to settings/screen changes, while the main window continues to own presentation output and automation. A window that needs other feature controllers should explicitly extend that composition boundary.
