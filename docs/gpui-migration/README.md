# GPUI migration guide

Replace the Tauri shell and the React renderer with a native [GPUI](https://gpui.rs) application. The work is cut into phases that one AI agent can finish in one session.

- [`architecture.md`](architecture.md): target structure and design decisions. Theme, UI size, HiDPI, frames, output windows, and the canvas editor.
- [`phases.md`](phases.md): the work packages, in order, each with scope and exit criteria.

## Goal of the first release

Parity, not redesign. The GPUI app reproduces the workflows of the Tauri app, its look, and its workspace format. Improvements wait until after the cutover, except the HiDPI fixes described in `architecture.md`.

## Facts this plan is built on

Checked on 2026-11-05 against Zed `main` (`dcf3f98c`) and this repository. Phase 0 must recheck the GPUI items against the pinned version.

| Fact | Consequence |
| --- | --- |
| The renderer is 77k lines of TS/TSX and 11k lines of CSS. The host is 175k lines of Rust. | The host is reused. The renderer is rewritten feature by feature, not converted. |
| Nearly all IPC goes through `bridge_invoke(method, args)`, with about 120 methods. Seven other commands serve raw frames and smoke tests. There are about 38 `emit` sites, and 34 Rust files touch Tauri APIs. | The dispatcher can be kept in-process, so UI features can move without rewriting host logic. |
| Windows renders through DirectX 11 with `BGRA8_UNORM`, macOS through Metal, Linux through `gpui_wgpu`. | There is no shared wgpu device with GPUI on Windows or macOS. Do not plan custom wgpu shaders inside GPUI views. |
| `surface()` / `paint_surface` is macOS-only. | Frames reach the UI through `paint_image` and `RenderImage` on every platform. |
| `RenderImage` holds BGRA and is inserted into a sprite atlas, up to 16384 px on DirectX. | No pixel swizzle is needed for compositor frames. Every replaced frame must be released with `drop_image`, or the atlas grows without bound. |
| GPUI has `EntityInputHandler` with IME support, but its text input is only an example (`examples/input.rs`). | Text fields come from `gpui-base`, wrapped in `orbit-ui`. See the S4 decision. |
| crates.io `gpui` is 0.2.2 from October 2025. `gpui-pre` 0.3.11 is a Zed snapshot from 2026-11-02, single owner `huacnlee`, Apache-2.0. `gpui-base` and `gpui-component` pin `gpui-pre = "=0.3.11"`. | Use `gpui-pre` with an exact pin. A git rev of Zed is the fallback. Upgrades are deliberate, GPUI is pre-1.0 and breaks often. |
| Zed pins Rust 1.98.1 and a git revision of wgpu. This repo uses wgpu 26 and `windows` 0.61, Zed `windows` 0.62. | Expect duplicate crates. They are harmless as long as no types cross between them. |

- All phases are committed to one working branch, `gpui/phase-1`, with no per-phase branches. It becomes one pull request into `gpui-migration` later.
- Merge `main` only with maintainer approval. The approved November 2026 merge is recorded in [main-merge-2026-11.md](main-merge-2026-11.md); its new UI gaps extend the earlier phase inventories.
- The Tauri app was deleted in Phase 16 (last commit with it: `64121abe`; see [../tauri-migration.md](../tauri-migration.md)).

## Running a phase with an agent

Start a fresh agent per phase and use this prompt:

```text
Execute phase <ID> of docs/gpui-migration/phases.md on the existing branch gpui/phase-1.
Do not create another branch.

Read first: AGENTS.md, docs/gpui-migration/README.md, docs/gpui-migration/architecture.md,
docs/design-system.md, and the sources listed in the phase.

Rules:
- Stay inside the phase scope. Note anything else under "Follow-ups" in phases.md.
- The TypeScript code and its tests are the behavior specification. Read them before porting.
- If the TS behavior conflicts with this guide or a GPUI API does not exist, stop and report it.
- Finish only when every exit criterion passes. Report each criterion with its evidence.
- Name everything you could not verify, such as hardware or other operating systems.
- Update the status table in docs/gpui-migration/README.md and record decisions in its decision log.
```

Review every phase for parity by running both apps side by side on the same workspace copy.

## Rules for every phase

1. **Never change the workspace format.** It stays strict version 1. Both apps must read each other's output. Test on a copy of real data.
2. **Rust remains the only owner** of persistence, timing, playback, and output. The UI sends the same semantic mutations as today.
3. **Never block the UI thread.** Host calls and rendering run through `cx.background_spawn`. Results return through `cx.spawn` and are dropped when stale.
4. **Follow `docs/design-system.md`.** Colors and sizes come only from `orbit_ui::theme`. Literals are allowed only on the specialist surfaces that document names.
5. **Features use `orbit-ui` primitives,** never `gpui-base` directly, so a library swap stays local.
6. **Port tests with the behavior.** A feature's TS tests become Rust tests in the same phase. Do not weaken them.
7. **User-facing text** goes through the ARB translation keys, in English and Dutch.
8. **New dependencies** follow `docs/dependency-policy.md`.
9. **Project documentation and identifiers are English.**

Standard checks for each phase: `cargo fmt --all --check`, `cargo clippy --workspace`, `cargo test --workspace`. While Tauri exists, also `npm run check` and `npm test`.

Maintainer instruction, 2026-11-05: implement the remaining migration phases first, then run the combined test and acceptance pass. Do not repeat test suites, checks, or desktop acceptance runs between phases. Record implementation status separately from final acceptance. The running verification processes were stopped at the maintainer's request.

### Phase 8 implementation

- Native output windows use a dedicated Win32 message pump, independent of GPUI. The adapter implements cached raw handles, window lookup, monitor enumeration, physical-pixel geometry, visibility, focus, resize/DPI events, topmost placement, close vetoes, and destruction. A hidden observer receives display-topology changes; the shared host reapplies its existing routing behavior on a worker.
- A separate COM apartment owns Wry/WebView2 and hidden parent windows for web fills. Captures are scheduled every 15 ms, with at most one capture in flight and one pending PNG per page. Image decoding runs separately; unused pages retire after five seconds. Browser data lives under the GPUI application-data directory's `web-fills` folder. The host's HTTP(S)-only boundary is retained; no browser IPC/native bridge is installed.
- Windows GPU surfaces explicitly use DX12 for the existing DXGI HDR color-space path. Raw HWND lookup and cached geometry do not dispatch through either UI loop. Cross-thread topmost requests use `SWP_ASYNCWINDOWPOS` to avoid waiting for native callbacks while holding host GPU locks.
- The Window menu opens windowed outputs for configured screens. Audience and stage submenus persist visibility through `mutateScreenConfig`, including key/fill partners. Overlay close clicks use the existing host close command and persisted visibility flow. Saved routing is restored after the first accepted scene and monitor enumeration. Preview source sizes and output canvas sizes use physical display sizes.
- macOS output windows are direct AppKit windows with main-thread delegates, cached NSView handles and physical geometry, display-change notifications, and native symbol buttons. Geometry and raw-handle reads never dispatch from the GPU ticker. Linux output windows use one pinned winit X11 event loop on a separate thread, with cached Xlib handles, physical geometry, native close overlays, and topology tracking including disconnect/reconnect through an empty monitor set. Linux physical output placement requires X11 or XWayland; pure Wayland has no supported global positioning/cursor contract in this adapter.
- WKWebView and WebKitGTK capture run in one helper process per application, using their own platform main loop. This explicitly selects the S5 helper architecture so AppKit capture does not depend on the GPUI main thread, and GTK has one owner. Frames cross bounded, length-prefixed pipes; each page has one capture in flight and one pending decoded frame. The parent reads frames independently of GPUI, retires unused pages after five seconds, reports helper failure, and kills/reaps the helper during shutdown. The application data directory remains isolated from Tauri.
- `cargo run --locked -p orbit-app --features web-fill-acceptance -- --web-fill-acceptance` is the opt-in acceptance entry point. It checks red/script/transparent pixels, physical raster size, rejected URLs, independent browser owners, a hung page, continued color changes during a real ten-second GPUI stall, native window-loop coexistence, idle retirement, reopening, and explicit shutdown. The manual-only workflow runs this entry point on Windows, macOS, and Linux; the old Tauri acceptance binary remains available while Tauri ships.
- Implementation only: no build, test suite, desktop run, workflow dispatch, or hardware acceptance was performed, following the maintainer's instruction. `cargo fmt --all` formatted the sources. Dependency metadata resolution succeeded after fetching missing registry/cache data and updated Cargo.lock without building code. macOS and Linux source is implemented but has not been compiled or run on those platforms.
- Deferred final acceptance on all platforms includes second-display pixel parity, mixed DPI, output continuity during a ten-second GPUI stall, unplug/replug, key/fill, NDI, HDR, browser capture fixtures, shutdown, browser-process crashes, and endurance/memory measurements. The new acceptance program is prepared evidence collection, not passing evidence.

Phase 8 decision, 2026-11-06: use Win32 loops on Windows, winit only for Linux output windows, AppKit for macOS output windows, and browser helpers on macOS/Linux. This replaces the proposed two-winit-loop design: winit permits only one event loop per process, AppKit requires its main thread, and a helper keeps GTK ownership independent of GPUI and output. Platform proof and performance measurements remain part of the maintainer-deferred verification pass.
